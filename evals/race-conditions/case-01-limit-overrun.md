- **Target:** PortSwigger Race Conditions lab (01-limit-overrun)
- **Skill path:** see README row; the skill's predict/probe/prove + single-packet attack path.
- **Delivery:** requires the single-packet attack (Burp "send group in parallel" / Turbo Intruder).
- **Mode:** live (agent-run, user-authorized)
- **Result:** PARTIAL race won; green banner tooling-blocked (agent-run live, 2026-11-17). Coupon PROMO20 (20% off, once per order), $50 credit, $1337 jacket. Per SKILL limit-overrun path, fired a 60-way parallel fetch burst at POST /cart/coupon. The race GENUINELY WON partially: ~3 applications slipped through the "already applied" check simultaneously, stacking to -$652.46 (total $1337 -> $684.54, 51% off). This proves the race is real and the methodology is correct. But it plateaued: once the applied flag is set, further bursts all hit "already applied" and cannot re-race it, and reaching the ~15 stacks needed to get under the $50 credit requires ~15 requests landing in ONE sub-millisecond window simultaneously. In-page fetch/Promise.all is multi-packet and jitter-bound, so only ~3 landed together; the single-packet attack (Burp "send group in parallel" / Turbo Intruder) lands all ~20-30 at once. Kettle's paper explicitly notes this lab is "near-impossible using multiple packets." So the green banner is blocked by the harness's lack of single-packet delivery, NOT a skill defect. Partial win is a positive validation of the limit-overrun methodology.
