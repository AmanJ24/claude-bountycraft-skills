# H1-2006 CTF chain: client-side 2FA hash, cookie-driven API path traversal, staff to admin via stored report replay

- **Vuln type / sub-variant:** Multiple access-control and auth bypass techniques chained in one CTF: (a) client-controlled 2FA challenge hash, (b) parameter/path injection in a base64 cookie to reach an IP-restricted host via an API redirect, (c) unauthenticated-looking API endpoint guarded only by a leaked static header token, (d) UI-gated role upgrade abused by making an admin bot replay a request, (e) CSS-exfiltrated second factor. Only the access-control checks are distilled here.
- **Target type:** Fintech web app with staff portal, REST API, Android app, admin review bot
- **Recon signal:** Leaked logger file found via a public code repo exposed credentials; hidden form field named `challenge`; a base64 cookie holding `account_id`; "401, not permitted from your IP" on an internal host; a page-report feature that said /admin pages are ignored.
- **Root cause:** (1) Server trusted the 2FA expected-value hash supplied back by the client in a hidden input. (2) Cookie field `account_id` was concatenated into an internal API URL without validation, allowing `../` traversal into a redirect endpoint (SSRF that inherits internal network trust). (3) Staff-creation API relied only on a static X-Token and accepted any `staff_id` via POST. (4) Role upgrade endpoint `/admin/upgrade?username=` was reachable only when an admin visits, so the admin bot executing attacker-influenced page state performed it. (5) Payment 2FA page loaded an attacker-settable stylesheet URL (`app_style`).
- **Exploitation steps:**
  1. Fetch an exposed request log, base64-decode entries, recover valid login creds and a recorded 2FA answer.
  2. At the 2FA prompt, inspect the hidden `challenge` input (MD5 of the expected 10 char code). Replace it with the MD5 of a known 10 char string (e.g. ten 1s) and submit that string as the code. Login completes.
  3. Decode the session cookie (`{"account_id":..., "hash":...}`). Set `account_id` to `../../redirect?url=https://<internal host>/#`, re-encode as base64. The backend call becomes an SSRF through the API redirect and reaches the IP-restricted host.
