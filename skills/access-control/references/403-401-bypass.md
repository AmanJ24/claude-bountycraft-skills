# The 401 / 403 bypass arsenal

Full detail behind SKILL.md section 4, from notes 02 (HackTricks), 10 (Clario `X-Rewrite-URL`), and 23 (Vidoc). A 401/403 is a claim the server makes; the question is whether it enforces it **identically** across every method, header, path encoding, and protocol. Use this whenever recon surfaces a forbidden-but-interesting endpoint. Confirm success means the **actual protected content or action**, not a 200 wrapper around a 403 body or a login page.

401 Unauthorized = not authenticated. 403 Forbidden = authenticated but not permitted. Both are bypassable through inconsistent enforcement.

## 1. HTTP method / verb fuzzing

A guard mapped to `GET` may not cover other verbs.
- Resend as `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`, `TRACE`, `CONNECT`.
- Try a **non-existent** verb (`FOO`); some stacks default it to GET handling while the guard ignores it.
- `HEAD` can leak existence/headers of a GET-protected page.

## 2. Header fuzzing (IP and URL overrides)

Defeat IP allowlists and front-end path routing. The Clario admin bug (note 10) was exactly `X-Original-URL`/`X-Rewrite-URL` reaching a front-end-blocked `/admin`.

URL-override headers (point the backend at the protected path while the front end sees a benign one):
```
X-Original-URL: /admin
X-Rewrite-URL: /admin
```
IP-spoof headers (with `127.0.0.1`, `localhost`, `10.0.0.1`, `172.16.0.1`, `127.0.0.1:80`):
```
X-Forwarded-For       X-Forwarded-Host     X-Real-IP
X-Remote-IP           X-Remote-Addr        X-Client-IP
X-Host                X-Forwarded-Server   X-Trusted-IP
Forwarded             Via                  Client-IP
```

## 3. Path fuzzing, normalization, and creative literals

Make the server resolve a different path than the guard matched. `/admin` -> 403? try:
```
/admin/            /admin/.              //admin//
/./admin           /%2e/admin           /%252e/admin
/admin/..;/        /admin;/             /admin..;/
/admin%00          /admin%20            /admin%09
/admin.json        /admin.html          /ADMIN   /Admin
/%2f/admin         /..%2f..%2fadmin     /%c0%af/admin
```
- **Case switching** against case-sensitive guards: `/User`, `/USer`, `/%75ser`.
- **Encoding layers**: single- vs double-encode the dot/slash (`%2e`, `%252e`, `%2f`, `%252f`); proxies and apps that normalize differently disagree on the final path.
- **Trailing additions**: trailing dot, semicolon params (`;jsessionid=`), matrix params.

## 4. Protocol downgrade

- HTTP/2 blocked? resend over **HTTP/1.1**, or **1.0 with the Host header removed** for unexpected routing.
- Combine downgrade with any other technique.

## 5. Hop-by-hop header abuse

Hop-by-hop headers are consumed by a proxy and not forwarded. List a header in `Connection:` to make the proxy **strip it** before the backend; if the backend relied on that header for the access decision, it may fail open.
```
Connection: close, X-Custom-Auth-Header
```
Standard hop-by-hop set: `Connection, Keep-Alive, Proxy-Authenticate, Proxy-Authorization, TE, Trailer, Transfer-Encoding`. Try stripping auth/identity headers the chain adds. This is only the first step; confirm it actually changes the access decision.

## 6. Framework and infrastructure quirks

- **Spring < 5.3**: `useSuffixPatternMatch` defaults true, so a mapping for `/admin` also matches `/admin.anything` (e.g. `/admin.json`) and can dodge a prefix guard.
- **Reverse-proxy vs app path mismatch**: the proxy enforces on one normalization, the app on another (the `X-Original-URL` family exploits this).
- **HTTP request smuggling**: a desync can route a request past a front-end auth/authz check entirely (deep topic; see smuggling-specific research).
- **User-Agent / Referer gating**: some apps serve different content by UA or trust an internal Referer; fuzz both.
- **SSO response tampering** (note 07): a misconfigured redirect leaks the full internal response; flipping `302 Found` to `200 OK` and deleting `Location` renders the protected app.

## Confirming a real bypass (avoid false positives)

- You must receive the **protected content or perform the action**, not a 200 that wraps the 403 body, an empty shell, or a login page.
- Diff the bypass response against both the original 403 and a known-good authorized response.
- A reflected header you control appearing in the response is not access; confirm the privileged data or function.

## Ordering heuristic

Method fuzzing and the `X-Original-URL`/`X-Rewrite-URL` pair pay out most often and are cheapest; run them first. Then IP headers, then path normalization/encoding, then protocol downgrade and hop-by-hop. Automate header/path lists with Intruder or ffuf, but verify each 200 by hand.
