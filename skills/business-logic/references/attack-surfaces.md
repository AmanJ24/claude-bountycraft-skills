# Business logic attack surfaces (feature classes)

Where logic flaws actually lived in this set. Each class lists the invariant it is supposed to enforce, the fields/signals to watch, and example reports (note numbers refer to `../../extracted/business-logic/`).

## Checkout / cart pricing
Invariant: the charged amount equals the catalog price for the real items and destination.
- Every money field the client sends is a candidate: `price`, `amount`, `total`, `subtotal`, `tax`, `shipping`, `discount`, `quantity`, `currency`.
- Negative quantity subtracts from the total while the internal-consistency check still passes (note 01, Upserve).
- Decimal quantity where units-granted and units-billed round differently (note 15, Krisp).
- Pricing inputs that are not the price: shipping country/region, tax-exempt flag, delivery method (note 06, Zyad).
- Integer overflow on price/quantity wrapping to zero or negative (note 05, Intigriti).
- The gateway handoff (cart -> PayPal/Stripe redirect) carries editable amounts, but is only a bug if the merchant fails to verify the paid amount afterward (note 04, WooCommerce: false positive).

## Coupons / promos / referrals / rewards
Invariant: each promo is used within its per-user, per-code, and expiry limits.
- Single-use offer accepted repeatedly, then raced after a partial fix (note 11, Stripe).
- Expired or already-redeemed coupons re-accepted; personal (birthday) coupons regenerated by editing a profile field; gift-card-with-discount recycling (note 05, Intigriti).
- Per-feature limit enforced only client-side; blank the "already selected" response to choose again (note 16, Curve).
- Self-referral, multi-accounting, free-trial reset via re-signup (note 12, OWASP; note 26, bitpanic).

## Subscription / plan / role gating
Invariant: paid or privileged features are available only to the entitled account.
- A paid-only role set by a client parameter on a free account (`access_level`, note 14, Lovable).
- Entitlement decided by a response boolean the client can flip (note 13, Streamlabs).
- A role/plan limit enforced only in the UI; the backend API does not re-check (note 25, secrets-mgmt; note 16, Curve).

## Multi-step and payment workflows
Invariant: later steps run only after their prerequisites, and each runs once.
- Skip the payment or approval step; call the completion/confirmation endpoint directly (note 23, PortSwigger; note 12, OWASP).
- Order-confirmation that reads an order id set in an earlier step without rechecking ownership (note 08, Intigriti).
- Double-processed/non-idempotent payment callbacks corrupting state (note 18, PortSwigger license; note 11, Stripe).

## OTP / 2FA / signup / claim flows
Invariant: the action proceeds only after the right actor proves control of the right resource.
- Omit the verification field entirely to reach an unvalidated path (note 19, hover.com OTP).
- A token/OTP not bound to the resource it authorizes, reused across objects (note 20, Eternal/Zomato).
- A policy gate (require 2FA) enforced on one path (submit) but not another (collaborator invite) (note 21, HackerOne).

## Balance / credit / ledgers
Invariant: a balance reflects only settled, final value.
- Credit granted on an observed upstream event that later reverts or never settles (note 09, Coinbase reverted transfer).
- Refund logic that does not detect a prior refund; withdrawal races (note 08, Intigriti).

## Licensing / seats / billing
Invariant: a purchase affects only its own license and is processed once.
- Non-idempotent purchase handling that merges/overwrites an existing license (note 18, PortSwigger).
- Seats-vs-price rounding mismatch on seat changes (note 15, Krisp).
